# FastNG: Modular Clean Architecture REST API Boilerplate

FastNG is a Fastify + TypeScript REST API boilerplate built on Modular Clean Architecture: Route → Controller → Service → Repository → Entity. Supports multiple database drivers (Prisma: sqlite/mysql/postgresql/sqlserver, Mongoose: mongodb) selected via `DB_DRIVER` env var. Modules are registered in a central registry and loaded via topological sort respecting declared `dependsOn[]` relationships. Each module owns its Prisma schema fragment (`db/*.prisma`), **its own migration history** (`db/migrations/`), a menu/permission manifest (`{name}.manifest.ts`), and its own `db/seeders/` (`*.json` table data or a `*.seeder.ts` escape hatch); `bun run migrate` diffs and migrates each enabled module independently via a Laravel-style migration CLI (disabling a module rolls its migrations back automatically), and `bun run db:seed` runs every enabled module's seeders. Authorization is dynamic RBAC (User → Role → Menu → Permission) with per-user allow/deny overrides and session-controlled refresh tokens. RBAC tables live in dedicated `permission`/`menu`/`role`/`session` modules (snake_case tables via Prisma `@@map`/`@map`); API docs are served by Scalar at `/docs` — see `tutorial/17`–`tutorial/24`.

## Non-Negotiable Rules

**Architecture & Code:**
- **Cross-module imports**: Only via the target module's `index.ts` (public API). Never import another module's internal files. `core/` never imports from `modules/`.
- **Entity**: Pure domain object. No imports from ORM (Prisma/Mongoose), Fastify, or any framework. May have domain logic methods.
- **Repository**: DB access only. Returns `Entity | null`, never throws domain errors (throw `NotFoundError` in the service instead). Responsible for mapping ORM ↔ Entity.
- **Service**: Contains all business logic and orchestration. Throws typed `AppError` subclasses. Never returns `null` for "not found" — must throw instead. Never directly touches `request`/`reply`/`fastify.*` or holds a raw DB client (always via injected repository).
- **Controller**: Parses input (Zod `safeParse`), calls service, formats output (`successResponse()`). No business logic, no try/catch — let errors propagate to the global handler.
- **Route**: Defines HTTP method/path/schema (JSON Schema for Swagger), attaches `preHandler` guards (e.g. `fastify.authenticate`). No business logic.
- **Registry**: Every new module must be declared in `src/registry/module.registry.ts` with `name`, `enabled` (boolean), `path` (ending in `.js` extension), and `dependsOn[]` (array of module names). Loader validates `dependsOn` are enabled at boot AND at migration time (`validateDependencies` in `src/registry/dependency-validator.ts`) — an enabled module whose dependency is disabled fails loudly in both.
- **Module manifest**: A module that is a sidebar menu (or exposes permissions) declares `src/modules/{name}/{name}.manifest.ts` exporting `manifest: ModuleManifest` (`menu` metadata or `menu: false`, plus `permissions: PermissionManifest[]` — each `{ code, name?, description, route? }`). Synced to the DB catalog bidirectionally by `bun run migrate` (or `bun run db:sync` standalone). See `tutorial/19`.
- **RBAC ownership & authorization**: RBAC tables are split across `permission`/`menu`/`role`/`session` modules; `auth` owns `users`, `user_roles`, `user_menu_permissions`. Effective permission = user override (allow/deny) over role grant; `can_access` gates a whole menu. Enforce only in route middleware via `fastify.authorize('menu','perm')` / `fastify.requireMenuAccess('menu')` — never in services. See `tutorial/22`, `tutorial/23`.
- **Module schema fragment**: A module with its own tables ships `src/modules/{name}/db/{name}.prisma` containing only `model` blocks (no `datasource`/`generator`). Fragments must be self-contained — never `@relation` across modules; use a scalar FK column. `prisma/schema.prisma` is AUTO-GENERATED by `src/core/database/schema-builder.ts` from enabled modules' fragments + the driver base block in `prisma/base/`; do not edit it by hand. See `tutorial/18`.
- **Module seeders**: Seed data belongs to the module that owns it — `src/modules/{name}/db/seeders/{table}.json` (default: `{ table, uniqueBy, rows, order? }`, values may use `{ "$env": "VAR" }` / `{ "$hash": <value> }`) or a `{what}.seeder.ts` escape hatch (`seeder: ModuleSeeder` = `{ name, order?, run(ctx) }`) for seed data that's dynamic or touches a composite-key table. Auto-discovered for enabled modules and run in registry topological order by `bun run db:seed` (`--module=` / `--class=` to narrow). A `*.seeder.ts` must go through the module's repository factory — never raw Prisma/Mongoose queries — and never seed domain data from `src/core/`. See `tutorial/26`.
- **Migrations**: `bun run migrate` diffs each enabled module's own fragment against its own previous snapshot — **never a combined diff** — and writes `src/modules/{name}/db/migrations/<ts>_<name>/{migration.sql, down.sql, schema.snapshot.prisma}` before applying it via `prisma db execute`. Batches live in the `_fastng_migrations` table (`module`/`migration`/`batch` columns, created by `migrate:install`), which is the source of truth — not `_prisma_migrations`. Disabling a module rolls its migrations back automatically on the next `migrate`. Never run `prisma migrate dev`/`db push` directly. See `tutorial/26`.
- **Import paths**: All TypeScript imports use `.js` extension (NodeNext ESM) even though source is `.ts`. Example: `import { UserService } from '../users/services/user.service.js'`.
- **Repository factory pattern**: `create{Name}Repository(fastify.db)` checks `env.DB_DRIVER === 'mongodb'` to return Mongoose or Prisma implementation; both conform to the same `I{Name}Repository` interface.
- **Multi-repository writes**: Only via `withTransaction(db, callback)` from `core/database/transaction.ts` (Prisma-only; throws for MongoDB). Each participating Prisma repository must expose `withClient(tx): I{Name}Repository`.
- **Service composition**: Service-in-service reuse only flows in the direction declared by `dependsOn[]`. Inject via constructor in `module.ts`, never `new ServiceX()` inside another service. Import only from the origin module's `index.ts`.
- **Package manager**: Use `bun`, not `yarn`/`npm`.

**Documentation & Versioning (Mandatory for All Changes):**
- **Update VERSION.md with every commit**: Track changes in `VERSION.md` using semantic versioning (MAJOR.MINOR.PATCH). Fundamental changes must include new tutorial(s); version bump determines changelog entry. See `VERSION.md` for versioning rules and commit format.
- **Create/update tutorial on fundamental changes**: Any new feature, pattern, or architectural change that is fundamental (not a routine bug fix) **must** have a corresponding tutorial file in `tutorial/NN-*.md` written in **Bahasa Indonesia**. See @.claude/rules/documentation.md for what counts as "fundamental", language requirement, and template format.
- **Tutorial is single source of truth**: The tutorial file is the definitive reference. Skills and rules files reference tutorials, not the reverse. Keep tutorials up-to-date in Indonesian.
- **Tutorial must accompany MAJOR/MINOR bumps**: No code commit for new patterns/features ships without tutorial. Tutorial MUST be done BEFORE commit.

## File Map

**Module structure**: `src/modules/{name}/{index.ts, module.ts, entities/, dto/, repositories/{name}.repository.ts + .prisma.repository.ts + .mongo.repository.ts, services/, controllers/, routes/, jobs/, db/{name}.prisma, db/migrations/, db/seeders/, {name}.manifest.ts}`

**Registry & loader**: `src/registry/module.registry.ts` (module declarations), `src/registry/topology.ts` (topological sort, shared), `src/registry/module.loader.ts` (boot-time loading), `src/registry/manifest.ts` (menu/permission manifests), `src/registry/seeder.ts` (`ModuleSeeder` contract + `loadSeeders()`)

**Migrations & seeding**: `src/core/database/migration/{migration.runner.ts, migration.files.ts, migration.ledger.ts}` (per-module diff/apply/rollback), `src/core/database/seeder/{json-seeder.ts, table-writer.ts}` (JSON seeder execution), CLI entry points `scripts/migrate.ts` / `scripts/db-seed.ts` / `scripts/db-sync.ts`

**Errors & responses**: `src/core/utils/errors.ts` (AppError subclasses), `src/core/middlewares/error-handler.ts` (global error handler), `src/core/utils/response.ts` (successResponse/errorResponse)

**Plugins**: `src/core/plugins/*.plugin.ts` (registered in `src/app.ts` in dependency order)

**Config & DB**: `src/core/config/env.config.ts` (Zod env schema), `src/core/database/transaction.ts` (multi-repo transaction utility)

**Versioning & Changelog**: `VERSION.md` (pure changelog tracking), `@.claude/rules/versioning.md` (semantic versioning rules and guidelines)

## Tooling & Conventions

**TypeScript**: 5.x, strict mode, NodeNext ESM (`moduleResolution: NodeNext`, all imports include `.js` extension)  
**Node**: >=20 (Bun used as package manager & dev/CLI runtime; `build` still compiles via `tsc`)  
**Framework**: Fastify 5  
**Package manager**: Bun (not yarn/npm)  
**Code style**: Prettier (`semi: false`, `singleQuote: true`, `trailingComma: 'es5'`, `printWidth: 100`, `tabWidth: 2`), ESLint flat config (typescript-eslint recommended, `no-console: off`)  
**npm scripts**: `bun run dev` (watch mode), `bun run build`, `bun run start` (prod), `bun run lint`, `bun run format`, `bun run migrate` (+ `migrate:install` / `:status` / `:rollback` / `:reset` / `:refresh` / `:fresh` — Laravel-style migration CLI, see `tutorial/26`), `bun run db:generate`, `bun run db:sync` (menu/permission catalog only), `bun run db:seed` (per-module seeders; `--module=` / `--class=`), `bun audit`  
**Documentation language**: All tutorial files in `tutorial/` folder MUST be written in **Bahasa Indonesia** (code samples/paths/identifiers remain in English). This ensures team accessibility regardless of English proficiency.  
**⚠️ No test framework installed yet**: vitest and supertest are listed in ARCHITECTURE.md as aspirational. Do not assume `bun test`, `vitest`, or `supertest` commands exist as a configured test runner in the current setup.
